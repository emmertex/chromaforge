# 26.46.0

## Develop

- **Two colour-grading modes (Eboda | Witchcraft):** Settings ▸ General grows a Grading Mode row beside Layout
  (`view.gradingMode`, Ctrl+Shift+G). **Witchcraft** — now the default — lays colour grading out the DaVinci
  Resolve way: after Basic, the Primaries palette with **two sets of wheels that both render at once** — the Color
  wheels (Lift / Gamma / Gain / Offset, wide overlap) and the Log wheels (Shadow / Midtone / Highlight / Offset,
  `primaries.logWheels.*`, narrow ranges placed by `primaries.low`/`high`; complimentary as in Resolve, the Color |
  Log tabs only pick which set is edited), each wheel at its own tuned strength (the Color set on the published
  ASC CDL shapes), then free-point **HSL Curves** (Hue vs Hue / Sat / Lum: points anywhere over the hue circle,
  `develop.hslCurves`); both sections carry a small Witchcraft pill beside their titles, and the Modern layout's
  Colour ▸ Color Grading card follows the mode. **Eboda** is the Lightroom Classic panels unchanged. The new engine
  controls (`ctl:primaries.*`) apply per channel after the tone map on the CPU and GPU alike (equivalence-tested),
  travel in presets, history and `lc:settings` XMP, and are one undo step per drag. A presentation choice: both modes
  edit the same photo. Beyond the reference app (Resolve-style grading, read as prose from Blackmagic's Colorist
  Guide; the maths is our own).

## Performance

- **The first start after an install or a driver update runs on the GPU:** building the graphics kernels with an empty driver shader cache took about 30 s on an RTX 4070 SUPER and an RTX 5070, as long as the start-up limit, so the app gave up on the card and edited on the CPU until the next start. The limit now counts from the last kernel built: a start that keeps building kernels gets the time it needs (up to 5 minutes), while a graphics driver that stops answering is still given up on after 30 s.
- **AI semantic search on the GPU on every OS (issue #896):** CLIP's transformer blocks run on wgpu kernels (layer norm, linear with GELU and residual fused, multi-head attention) on Vulkan, DX12 and Metal, replacing the macOS-only candle Metal path. A tower is checked against the CPU on a test input before use, and any GPU error moves the job back to the CPU with the reason shown.

## Fixes

- **Plug-in calls no longer fail at a fuel slice:** plug-in modules are compiled when loaded instead of function by function as they first run. wasmi charged a function's compilation to the call's fuel and couldn't resume an out-of-fuel during one, so a long call failed with "instruction budget" whenever a first run fell at the end of one of the host's fuel slices. Loading costs 1.2 to 3.4 ms more per plug-in (108 to 296 KB modules); calls cost nothing more. PR #909.
- **Synchronize Folder:** a scan is no longer refused after you rate, tag or edit the folder's photos while it runs, and a moved file is relinked only if it still has the content the scan read.
- **Lens corrections:** a raw's in-file lens correction is recorded in the catalog when it is decoded, so the Optics panel and the render agree.

## Plug-ins

- **Plug-in jobs:** a plug-in command declared as a job (`"job": true`, host feature `jobs`) runs on a worker with a row in the activity stack. It reports its progress, what it is working on and the photos done or failed (`job.*` host calls), stops between calls when the row's ✕ is clicked, and continues past one call's budget with `{continue: state}`. A job may read the catalog but not change it yet. `plugin.run {wait: true}` runs one to its end from the CLI and MCP. The SDK has `job::*` helpers and a `job-tools` example.
- **A plug-in can look at a photo and set its crop:** `photo.pixels` (permission and host feature `pixels`) gives a downsized copy of the uncropped frame as 8-bit sRGB, and `develop.setCrop` (permission and host feature `crop`) sets the crop and straighten angle in that frame as one History step. A job may read pixels but not set a crop. The SDK has `host::photo_pixels` and `host::set_crop`, and decodes base64 about five times faster. PR #891.
- Pixel filters: `develop.pluginFilter.analyze` takes `ids` (a batch, each photo measured on its own) and `roll: true` (one measurement for all of them, from the module's new optional `pc_merge` export; stored on each with `_roll`); `develop.pluginFilter.applyTo` copies an entry onto the other photos. The panel offers them as Measure ▾ and *Apply to N*, shows the measurement's state, lays manifest `sections` out as foldable headings and aligns its menus and switches with the sliders. A manifest `shortcut` makes the filter an *Add <name>* command with that key (`develop.pluginFilter.addTo`), rebindable in Keyboard Shortcuts. PR #889.
- **A plug-in can make a virtual copy of a photo:** `photo.virtualCopy {photo, name?}` (permission and host feature `virtualCopy`) makes one as *Create Virtual Copy* does, stacked with the photo and in its albums, named `name` or the next "Copy N", as one History step, and returns the copy's id. With `develop.setCrop` a plug-in can split one capture into several photos, such as two half-frame exposures in one 35 mm scan. Prepare steps and jobs can't call it. The SDK has `host::virtual_copy`. PR #891.
- **Plug-ins carry their own icon and header:** a plug-in's manifest may carry `icon` and `header` SVGs as a pixel filter's does (same size limit and untrusted drawing). The Plug-in Manager shows the icon in its list and on the plug-in's page, the header in place of the plug-in's name, and its command dialogs show the header above their title. `plugin.list` shows both as booleans and `plugin.picture` serves them for plug-ins too. PR #912.
